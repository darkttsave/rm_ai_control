# Playbook --- RM Project Assimilation

> v2.3 继承：**造不造得出来 + 出问题会不会修**。

> 场景：接手学长成熟工程、校队已有仓库或重要开源项目。\
> 目标：尽快获得工程控制力，而不是先读完全部源码或重构整个项目。

------------------------------------------------------------------------

# 1. Brownfield First

第一原则：

> **先继承，再改造。**

不要一接手就：

-   迁移目录；
-   重命名全部模块；
-   重写配置系统；
-   用自己的 Framework 覆盖原文档；
-   因为"看起来不优雅"立即重构。

先确认它是否真的能工作，以及原作者如何使用它。

------------------------------------------------------------------------

# 2. Engineering Control Ladder

  Level            能力         判定问题
  ---------------- ------------ ----------------------------------------------
  L0 Reproduce     跑起来       能否构建、启动并复现预期结果？
  L1 Operate       会使用       知道入口、输入输出、日志和正常现象吗？
  L2 Tune          会调         知道关键参数影响、方向、范围、观测与回滚吗？
  L3 Diagnose      会定位       能把异常缩小到合理模块/边界吗？
  L4 Modify        会安全修改   理解当前约束、接口和验证方法吗？
  L5 Explain       能解释       能说明原理、工程语义和 trade-off 吗？
  L6 Reconstruct   能重建       没有现成实现能重新设计并验证吗？

不是所有模块都需要达到 L6。

开始任务时问：

> 当前责任真正要求我达到哪一级？

------------------------------------------------------------------------

# 3. 推荐接管顺序

## Step 1 --- Reproduce

搞清：

-   build；
-   runtime environment；
-   dependency；
-   hardware requirement；
-   config；
-   expected output。

确认原 baseline 是否真的可复现。

如果不能复现：

> "不能复现"本身就是事实。

不要先修改再假装原系统正常。

------------------------------------------------------------------------

## Step 2 --- Operate

至少知道：

-   怎么启动；
-   怎么停止；
-   输入来自哪里；
-   输出去哪；
-   日志在哪里；
-   可视化怎么看；
-   哪种现象叫正常。

------------------------------------------------------------------------

## Step 3 --- Tune

找出真正会在赛场使用的关键参数：

-   参数含义；
-   增大/减小趋势；
-   合理范围；
-   调整时观察什么；
-   回滚方式；
-   哪些参数不能随便改。

不是把所有 YAML 字段都解释一遍。

------------------------------------------------------------------------

## Step 4 --- Map

在已经运行过系统以后，再建立简洁主链路：

``` text
Input
→ Main Modules
→ Critical State
→ Output
```

只深入当前负责区域和必要上下游。

------------------------------------------------------------------------

## Step 5 --- Diagnose

通过真实问题或受控故障建立：

-   正常信号是什么；
-   异常首先会在哪里表现；
-   模块边界怎样定位；
-   第一批应获取什么证据。

达到这一步以后，开发者才真正开始拥有工程控制力。

------------------------------------------------------------------------

## Step 6 --- Modify / Evolve

需要修改时：

-   明确 Scope；
-   明确 Required Verification Level；
-   先保护外部 Contract；
-   修改后重新建立 baseline；
-   重要 Milestone 后做 Convergence。

------------------------------------------------------------------------

# 4. 没有本地传承时

如果方向没有学长成熟实现，例如新兵种或新技术路线：

不要只盯一个开源仓库。

可按需进行：

``` text
多个开源项目 / 论文 / 报告
→ Reference Triangulation
→ 复现若干 baseline
→ 找共同结构与关键差异
→ 再做最小原型
→ Experiment
```

Issues、PR、Commit
History、比赛报告可以在必要时作为"虚拟学长"恢复演化原因。

但这属于按需 Evidence Mining，不是所有项目接管的强制步骤。

------------------------------------------------------------------------

# 5. Assimilation 阶段不追求什么

不追求：

-   完整理论学习；
-   完整源码阅读；
-   完美新人文档；
-   统一所有命名；
-   大规模架构重构；
-   把历史所有问题一次解决。

目标只有：

> **让我能够安全使用、调节、定位，并知道下一步真正需要学什么或改什么。**
