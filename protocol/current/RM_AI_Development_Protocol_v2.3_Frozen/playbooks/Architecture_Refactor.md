# Playbook --- Architecture / Refactor

> v2.3 继承：**稳不稳定**。

> 场景：明确进入结构收敛或重构阶段。\
> 原则：**Architecture 是显式模式，不是 Delivery 中途的冲动。**

------------------------------------------------------------------------

# 1. 什么时候值得进入 Architecture

合理触发：

-   当前结构阻塞新功能；
-   同一问题已经出现多份重复实现；
-   模块职责长期混乱；
-   接口边界导致每次功能都跨大量文件修改；
-   旧路径和新路径已经共存；
-   Temporary 开始变成永久复杂度；
-   一个 Milestone 已经稳定，适合集中收敛。

不充分的理由：

-   "看起来还能更优雅"；
-   "以后可能有十种 Provider"；
-   "成熟开源项目都用了 Factory"；
-   "AI 建议做一层抽象"。

------------------------------------------------------------------------

# 2. 重构前必须有 Baseline

至少知道：

-   当前正常行为；
-   关键测试；
-   关键配置；
-   外部接口；
-   当前验证等级。

没有 baseline 的重构，很难知道自己是否只是换了一种 Bug。

------------------------------------------------------------------------

# 3. 先明确重构要减少什么

真正有效的 Architecture 应至少减少一种负担：

-   概念数量；
-   重复路径；
-   跨模块耦合；
-   无意义配置；
-   变化影响范围；
-   阅读主链路时的噪音。

如果结果只是：

``` text
新增 Factory
新增 Manager
新增 Adapter
新增 Config
旧实现全部保留
```

则高度可疑。

------------------------------------------------------------------------

# 4. 重构允许一次修改多个相关文件

"最小修改"不是 Architecture 的目标。

目标是：

> **形成当前需求下最小、清楚的最终结构。**

因此内部破坏性修改是允许的，只要：

-   Scope 明确；
-   外部行为是否改变已明确；
-   需要改变公共行为时触发 Human Gate；
-   修改后重新验证。

------------------------------------------------------------------------

# 5. 删除优先

重点检查：

-   无调用者旧 API；
-   Deprecated wrapper；
-   不再使用的 Mode；
-   永远只有一个真实值的 Config；
-   已被新方案完全取代的 Algorithm；
-   临时兼容；
-   重复 Helper；
-   `utils/others/misc` 中职责已经明确的代码。

历史由 Git 保存。

------------------------------------------------------------------------

# 6. 模块应该允许增量演化

一个模块第一次 Baseline 后，未来为了新功能回来修改是正常的。

例如：

``` text
Player v1
→ Bullet 需求
→ Player 增加有限 shoot 接口
```

对应 RM：

``` text
Detector Baseline
→ MultiFrame 需求
→ 新增 Recognizer
```

健康变化应主要发生在有限区域。

如果每增加一个小能力都必须同时改：

``` text
Camera
Detector
StateMachine
Serial
Config
main
```

说明抽象边界值得审查。

------------------------------------------------------------------------

# 7. Architecture 完成后

必须：

1.  重新跑 baseline；
2.  检查外部 Contract；
3.  删除过渡代码；
4.  更新必要 Project State；
5.  输出完整 Task Report；
6.  确认是否真正减少了复杂度。

重构不是项目美化，而是恢复工程可控性。
