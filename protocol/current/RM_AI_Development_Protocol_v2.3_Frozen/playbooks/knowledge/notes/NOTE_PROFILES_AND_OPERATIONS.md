# Note Profiles & Operations

> 用于决定“这份知识资产应该长什么样，以及是新建、更新还是合并”。
>
> 用户不需要手动选择内部标签；AI 根据内容和 Asset Index 判断，并在影响现有资产时说明。

---

# 1. Note Types

## 1.1 Theory / Concept

适合：

- PnP / EKF；
- 数学 / 算法；
- 坐标系；
- 控制 / 气动概念。

常用结构：

```text
一句话本质
→ 核心关系 / 图
→ 前置对象
→ 核心概念
→ 关键关系
→ 为什么成立
→ 易混 / 边界
→ 在系统中的位置
```

当前阶段不需要的完整推导不要强行加入。

---

## 1.2 API / Code

适合：

- OpenCV；
- ROS2；
- C++ / SDK；
- 代码阅读中的稳定机制。

第一屏优先：

- 正式签名 / 常用形式；
- 输入 / 输出；
- 高频参数；
- 最小示例；
- 当前 Pipeline 位置。

原则：

> **先能查，再能读。**

正文再解释：

- 核心机制；
- 高频模式；
- 运行时语义；
- 常见错误；
- 强相关知识。

---

## 1.3 System / Architecture

适合：

- RM Pipeline；
- ROS 系统；
- Agent Workflow；
- 多模块架构。

优先给：

```text
Input
→ Module / State
→ Module / State
→ Output
```

然后按数据 / 状态流讲：

- 输入；
- 模块职责；
- Contract；
- 接口；
- 失败 / 边界；
- 当前工程位置。

---

## 1.4 Engineering / Project

适合：

- 某个真实任务总结；
- 实验结论；
- 特定工程约束；
- 复现 / 调参 / 联调过程中形成的可复用知识。

必须区分：

```text
通用知识
当前项目事实
当前配置 / 参数
验证状态
```

不要把一次项目参数伪装成普适结论。

---

# 2. Operations

## 2.1 New

使用条件：

- 当前形成独立知识职责；
- Asset Index 中没有同职责 Canonical Asset。

创建后建议更新 Asset Index。

---

## 2.2 Update

使用条件：

- 已有 Canonical Asset；
- 本轮只是补全、纠错或深化同一主线。

默认优先 Update，而不是因为“这次学得更详细”再创建第二篇同职责笔记。

重要更新应保留：

- 原主线仍然可读；
- 新知识放在正确依赖位置；
- 已失效内容被明确修正。

---

## 2.3 Merge / Supersede

使用条件：

```text
同主题
+
同职责
+
长期会造成重复入口 / 冲突
```

操作前必须说明：

- 哪些内容重复；
- 哪份适合作为主入口；
- 哪些独有内容要保留；
- 旧资产是删除、保留历史还是标 Superseded。

涉及真实知识库文件移动 / 删除 / 重命名时，遵守 Human Gate；不要自行破坏旧资产。

---

## 2.4 Legacy Reconstruction

用于：

> 旧笔记 / 旧学习任务已经有历史价值，需要重新组织为长期知识资产。

核心约束：

### 原始材料默认只读

不要覆盖旧来源。

### Semantic Coverage

不是要求逐字复制，而是保证：

- 原始问题；
- 有价值注释；
- 用户原创理解；
- 实际任务事实；
- 历史验证结果；

都有明确去向。

### 历史状态和当前重构状态分开

```text
Original Task Status
= 当时用户真实完成 / 验证到哪里

Rewrite Status
= 本次重构实际检查了什么
```

不能因为当前没有硬件，就把历史“已实机验证”改成“未验证”。

同样不能因为做了结构检查，就声称代码行为已验证。

### 技术校正

旧材料明显不严谨时：

- 保留原问题 / 学习背景；
- 给出更准确表述；
- 不伪装成原始来源本来就这样写。

### 任务驱动旧笔记

同时保留：

```text
最终清晰主流程
+
原始问题链中具有长期认知价值的部分
```

不要只留下漂亮教程，也不要因为保留历史而让主流程继续破碎。

### Source Inventory / Source Map

正式重构前，按实际 Scope 盘点：

- 来源文件；
- 图片；
- 代码样例；
- 用户原创总结；
- 问题；
- 代码注释；
- 已声明的验证结果。

重构完成后，重要来源应能找到明确去向。

### 代码注释的去向

有学习价值的注释按以下方式处理：

1. Retain in place：准确、简短、紧贴语句；
2. Rewrite in place：学习目的保留，但改成更准确表述；
3. Move and expand：长原理 / 问题移到正文，代码保留短提示；
4. Historical correction：真实错误或演化过程放到纠错 / 历史区域。

只有纯重复或噪声才能在确认无独有信息后删除。

### Staged Approval

如果用户要求分批审理：

```text
先 Audit，不写文件
→ 提出整体结构
→ 只实现已批准批次
→ 报告本批变化与剩余内容
→ 用户确认后继续
```

一批批准不代表可以顺手重组无关知识库。

# 3. Asset Decision

用户说“整理成笔记”时，AI先内部判断：

```text
当前中心问题是什么？
↓
Asset Index 是否已有同职责资产？
↓
New / Update / Merge / Legacy Reconstruction
↓
选择 Note Type
↓
按 NOTE_CORE + NOTE_STYLE_STANDARD 生成
```

如果会修改 / 合并现有正式资产：

> 简短说明判断和影响，让用户拥有最终决定权。

如果只是新建独立笔记：

> 不需要让用户先学习内部 Operation 名称。
