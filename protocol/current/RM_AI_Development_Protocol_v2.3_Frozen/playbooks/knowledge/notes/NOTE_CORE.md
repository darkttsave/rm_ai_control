# Note Core — 正式技术笔记总约束

> 目标：把已经讲清楚 / 学过 / 有来源材料的内容整理成**可快速复习、结构稳定、长期可维护**的知识资产。
>
> 核心：**按知识依赖组织，不按聊天顺序组织；讲解可以展开，笔记必须收紧。**

---

# 1. 一篇笔记先有唯一主线

生成前先回答：

> 这篇到底解决什么？

“一篇一条主线”不等于“一概念一文件”。

多个概念可以共存，只要共同服务同一个中心问题。

需要拆篇的判断依据是：

> 是否已经出现第二条独立主线？

---

# 2. 知识结构优先于对话顺序

禁止：

```text
我们先聊 A
后来问 B
又补 C
→ 笔记也按 A / B / C 原样抄
```

应重新组织成类似：

```text
本质
→ 前置对象
→ 核心概念 / 机制
→ 关键关系
→ 为什么成立
→ 工程意义
→ 易混 / 边界
→ 回到系统位置
```

顺序由知识依赖决定。

---

# 3. 快速复习信息前置

第一屏优先让未来的用户快速恢复：

- 一句话本质；
- 最重要关系；
- 核心图 / 公式 / API / 流程；
- 本篇最需要记住的结论。

不要先铺大段背景。

不同 Note Type 的第一屏可以不同，具体见：

`NOTE_PROFILES_AND_OPERATIONS.md`

---

# 4. 讲解可以详细，正式笔记必须收紧

流程：

```text
详细讲解
→ 追问 / 纠错
→ 理解收敛
→ 重新组织
→ 正式笔记
```

正式笔记通常删除：

- 聊天式过渡；
- 同义重复；
- 已解决但无长期价值的来回争论；
- 不影响主线的扩展背景。

必须保留：

- 最终正确模型；
- 关键因果链；
- 容易重新混淆的纠错点；
- 对后续知识有接口价值的结论。

---

# 5. 来源事实、解释、推断分层

不能为了文章顺畅把不同可信度写成一种语气。

可按需标记：

## 来源明确

```markdown
资料明确给出：……
```

## 直观理解

```markdown
> **直观理解：** ……
```

## 工程理解 / 迁移

```markdown
> **工程理解：** ……
```

## 知识校正

```markdown
> **知识校正：**
> 原材料表述为……
> 更准确应理解为……
```

如果来源没有支持某个点，不要静默补成“来源内容”。

---

# 6. “一些问题”只放长期有价值的补充

适合：

- 易混概念；
- 常见误解；
- 特殊情况；
- 近似边界；
- “为什么不是……？”；
- 不适合打断主干的纠错。

但：

> 如果一个概念是理解主线所必需，就必须放回主线。

“一些问题”不是垃圾桶。

---

# 7. 图、公式、代码都必须承担认知任务

不要因为“看起来空”就加图。

不要因为“理论笔记”就堆公式。

不要因为“工程笔记”就贴大段源码。

每个元素都应回答：

> 它为什么必须出现在这里？

具体格式见：

`NOTE_STYLE_STANDARD.md`

---

# 8. 主干自洽，链接负责继续深入

不能只写：

> 这里很关键，去看另一篇。

当前笔记必须先给够继续阅读所需的最小解释。

然后再链接：

```markdown
> 这里先记住：……
>
> 详细机制见：[[XXX]]
```

---

# 9. 篇幅控制看主线，不看字数

允许长，但不能：

- 同时存在两条独立主线；
- 一个结论反复解释；
- 为“完整”塞入所有未来知识；
- 把整个知识树提前展开。

原则：

> **宁可留下明确接口，也不要提前展开整片知识树。**

---

# 10. 生成工作流

```text
1. 检查 Asset Index
2. 判断 New / Update / Merge / Legacy Reconstruction
3. 一句话确定中心问题
4. 列知识依赖链
5. 确定第一屏
6. 写主干
7. 整理易混 / 边界
8. 回到工程 / 系统位置
9. 压缩聊天残留和重复
10. 更新 Asset Index 建议
```

操作规则见：

`NOTE_PROFILES_AND_OPERATIONS.md`

---

# 11. 最终质量标准

## 第一眼

> 我马上知道这篇最重要的是什么。

## 顺着读

> 每个新概念建立在前面的概念上，没有突然跳跃。

## 以后回来

> 我能快速恢复记忆，并知道下一步应该深入哪里。

最终目标不是记录最多，而是：

> **让知识长期保持可进入、可理解、可复用。**
