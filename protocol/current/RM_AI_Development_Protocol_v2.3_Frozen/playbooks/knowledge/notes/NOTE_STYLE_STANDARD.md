# Note Style Standard — 正式笔记格式规范

> 本文件只约束正式 Knowledge Note。
>
> 普通讲解对话不需要遵守这些排版规则。

---

# 1. 标题

标题负责定位，正文负责解释。

推荐：

```text
# 平面 PnP 多解
## Homography 与位姿恢复
## 两个候选解
## 易混点
```

避免：

> 把完整结论、背景、动机全写进标题。

默认层级控制在：

```text
# 主章节
## 二级说明
### 局部问题 / 小节
```

除非确有需要，不继续堆更深层级。

---

# 2. 第一屏

根据 Note Type 选择最有用的信息前置。

通常优先：

```text
一句话本质
核心关系 / 流程
核心公式 / API
最重要结论
```

API / 工程型笔记优先“能查”。

理论型笔记优先“恢复模型”。

系统型笔记优先“看到数据 / 状态流”。

---

# 3. 数学公式

## 3.1 符号先定义

不要让公式突然出现。

先说明：

```text
θ：机体俯仰角
γ：轨迹角
α：攻角
```

再写：

\[
\alpha \approx \theta - \gamma
\]

## 3.2 公式旁边说明“回答什么”

例如：

> 这条关系表达机体朝向与实际飞行方向之间的差值。

## 3.3 近似必须写边界

如果只在：

- 二维；
- 小角度；
- 忽略侧滑；
- 特定模型假设；

下成立，紧邻公式说明。

## 3.4 Markdown / LaTeX

行内公式：

```markdown
$Z_c$
```

独立公式：

```markdown
$$
x_n = \frac{X_c}{Z_c}
$$
```

保持符号风格一致，不混用同一变量的多套记法。

---

# 4. 代码

代码块必须标语言：

````markdown
```cpp
cv::solvePnP(...);
```
````

优先：

- 最小可理解示例；
- 与正文关系紧密的关键片段；
- 必要注释贴近对应语句。

不要为了“完整”整段复制不相关源码。

如果来源代码有长期有价值的学习注释，Legacy Reconstruction 时按其规则保存。

---

# 5. 图片

图片必须承担一个明确问题。

用户后续补图时使用：

```markdown
> 【插图｜名称】
>
> 建议内容：
> - ...
> - ...
>
> 这张图负责说明：...
```

不要只写：

```text
【这里放图】
```

关系第一次建立时就尽量放图，不要很晚才补。

---

# 6. 来源与不确定性

如果任务指定来源：

- 来源事实按来源实际内容写；
- 模型补充不能伪装成来源；
- 外部纠错明确标记；
- 来源未给出就写“来源未给出 / 待确认”。

允许：

```text
Unknown
待验证
当前理解
来源未明确
```

不要为了文章完整而猜。

---

# 7. 内部链接

链接负责复用成熟知识，不负责逃避当前解释。

推荐：

```markdown
这里先记住：相机坐标经过透视除法得到归一化坐标。

详细推导见：[[针孔投影模型]]
```

不要：

> “这很重要，见另一篇。”

然后当前主线完全无法继续。

---

# 8. 表格与列表

表格适合：

- 多个固定字段比较；
- API 参数；
- 相似方法差异；
- 状态 / 选项选择。

列表适合高密度枚举。

不要把多个独立事实压成一个超长粗体段落。

---

# 9. 语言风格

正式笔记：

- 直接；
- 清晰；
- 可扫描；
- 工程化；
- 少对话式过渡；
- 默认用户已有正常 C++ / 数学 / 工程基础；
- 需要详细时把因果讲清楚，而不是把句子写得更长。

推荐：

> **姿态描述机体朝向，轨迹角描述速度方向。**

不推荐大量：

> “那么这个时候我们就可以发现……”

---

# 10. 输出前检查

- [ ] 第一屏能快速恢复本篇；
- [ ] 标题短且可扫描；
- [ ] 公式符号已定义；
- [ ] 近似边界已说明；
- [ ] 代码块有语言；
- [ ] 图承担明确任务；
- [ ] 来源事实与解释 / 推断已分开；
- [ ] 链接没有替代必要解释；
- [ ] 没有为了高级而扩展无关知识；
- [ ] 主线仍然只有一条。
