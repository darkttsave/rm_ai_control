# Explanation Profiles — 对象与深度增量规则

> Profile 只补充 `EXPLANATION_CORE.md`。
>
> 不复制父层规则，也不要求用户手动选择。

---

# 1. Subject Profiles

## 1.1 Theory / Concept

适合：

- 数学 / 算法；
- PnP / EKF；
- 控制 / 气动；
- 抽象工程概念。

常用路径：

```text
为什么需要
→ 对象 / 直觉
→ 关键关系
→ 条件 / 边界
→ 工程意义
→ 与已有知识连接
```

如果数学是当前断点，再进入推导。

不要因为主题“理论性强”就默认完整证明。

---

## 1.2 Code

适合：

- 阅读源码；
- 看懂函数 / 类 /调用链；
- 理论映射到实现。

优先回答：

```text
这段代码在整个流程里负责什么
→ 输入是什么
→ 关键状态怎么变化
→ 输出去哪里
```

需要时分层：

```text
语言层
框架 / API 层
业务逻辑层
算法 / 原理层
```

逐行讲解只在：

- 某几行语义本身就是断点；
- 生命周期 / 所有权 / 模板等细节真正影响理解；

时使用。

---

## 1.3 API / Framework

适合：

- OpenCV；
- ROS2；
- SDK；
- Library / Runtime。

优先建立：

```text
调用者提供什么
→ API / Framework 何时执行
→ 它负责什么
→ 返回 / 状态变化是什么
→ 当前工程怎样使用
```

工程速用时重点：

- 正式接口；
- 高频参数；
- 输入输出；
- 最小示例；
- 常见坑；
- 版本边界。

不要把 API 参考回答自动扩成完整内部实现课程。

---

## 1.4 System / Architecture

适合：

- Pipeline；
- ROS 系统；
- Agent Workflow；
- 多模块工程。

优先：

```text
输入
→ 主要模块
→ 关键状态 / Contract
→ 输出
→ 失败边界
```

区分：

- 当前实现事实；
- 设计意图；
- 可替代方案；
- 未来设想。

如果用户只是要建立系统地图，不要提前钻进每个模块细节。

---

# 2. Depth / Control Need

这不是固定 Mode，而是当前任务要求的理解深度。

---

## 2.1 Engineering Use

目标：

> **先能正确使用，不把系统当盲盒。**

至少覆盖：

- 它解决什么；
- 输入 / 输出；
- 当前怎么调用 / 接入；
- 关键参数；
- 当前 Pipeline 位置；
- 高频错误；
- 出问题第一步查哪里。

通常对应 Engineering Control L1～L2。

---

## 2.2 Working Understanding

目标：

> **能够 Tune / Diagnose / Modify 当前相关部分。**

在 Engineering Use 上增加：

- 核心内部模型；
- 参数为何影响结果；
- 正常行为与异常信号；
- 关键假设 / Invariant；
- 常见失效模式；
- 输入变化如何传播到输出；
- 修改影响范围与验证点。

通常对应 L2～L4。

---

## 2.3 Deep Study

目标：

> **该主题已成为长期核心能力，需要形成完整可迁移理解。**

按需增加：

- 数学结构；
- 必要推导；
- 不同方法比较；
- 理论边界；
- 源码映射；
- 历史 / 现代扩展；
- 与其他知识节点的关系。

通常接近 L5 / L6，但 Deep Study 本身也不等于工程验证。

---

# 3. 组合示例

```text
Code + Engineering Use
→ 先看职责、调用链和关键语义

API + Working Understanding
→ 接口 + 参数机制 + 失效模式 + 排查

Theory + Deep Study
→ 直觉 → 数学 → 边界 → 工程 → 方法关系

System + Engineering Use
→ 先建立主数据流和模块地图
```

AI可以在同一对话中动态改变组合，不需要换聊天。
