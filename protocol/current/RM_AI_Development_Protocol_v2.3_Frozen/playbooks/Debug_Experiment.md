# Playbook --- Debug / Experiment

> v2.3 继承：**出了问题会不会修**。

> 场景：系统行为异常，但原因尚未确认。\
> 核心目标：**获得证据，不是增加修改数量。**

------------------------------------------------------------------------

# 1. Investigation 与 Delivery 分开

当原因未知时，不要直接进入"完整修复"。

先写出：

``` text
Phenomenon
Facts
Unknowns
Hypotheses
Evidence Needed
```

允许：

-   加日志；
-   保存现场；
-   查数据；
-   读代码；
-   写一次性测试脚本；
-   做可撤销 instrumentation。

默认不允许：

-   同时加入多个永久 fallback；
-   大规模重构；
-   为每个假设各写一条生产路径。

------------------------------------------------------------------------

# 2. 描述问题

一个好的问题描述至少包括：

## Phenomenon

具体发生什么。

不要只写：

> "识别不稳定。"

而写：

> "侧视角约 XX° 后，Detector 输出经常为空；正视条件相同曝光下稳定。"

## Known Facts

已经确认：

-   输入是否存在；
-   时间戳；
-   参数；
-   当前软件版本；
-   硬件状态；
-   哪些路径正常。

## Unknowns

真正不知道什么。

------------------------------------------------------------------------

# 3. 建立有限假设

先提出少量高概率候选。

例如：

``` text
H1 数据分布问题
H2 曝光问题
H3 threshold 过滤
```

AI 可以帮助：

-   找逻辑硬伤；
-   补高概率遗漏；
-   按概率或信息增益排序。

不要让 AI 从零生成几十个"所有可能原因"。

------------------------------------------------------------------------

# 4. 选择下一次最大信息量实验

问：

> 如果只能做一次测试，哪个测试能最大程度区分这些假设？

优先：

-   成本低；
-   风险低；
-   可回滚；
-   结果可解释；
-   能排除多个候选。

------------------------------------------------------------------------

# 5. 一次实验围绕一个主要变量

结构：

``` text
Hypothesis
→ Controlled Change
→ Measurement
→ Result
→ Conclusion
```

例如验证曝光：

-   只改变曝光；
-   保持模型、threshold、NMS、姿态条件尽量不变；
-   记录结果；
-   再决定下一步。

如果现实使多个变量无法分离：

> 明确记录限制，不声称单变量因果。

------------------------------------------------------------------------

# 6. 实验结果要产生知识

实验结束至少回答：

``` text
支持了什么？
排除了什么？
仍然不知道什么？
下一步是否进入 Delivery？
```

如果实验没有改变任何判断，只是"又试了一次"，应重新设计实验。

------------------------------------------------------------------------

# 7. 修改代码前先收敛结论

证据足够后，再进入 Delivery：

``` text
Confirmed Problem:
Chosen Fix:
Expected Behavior:
Failure Behavior:
Verification:
```

这时 AI 可以高速实现。

------------------------------------------------------------------------

# 8. 真实机器人实验

需要人上车/接线/调相机时，AI 应把实验压缩成：

``` text
验证：
操作：
观察：
A → 说明什么
B → 说明什么
```

不要让人连续改五个参数再回来告诉 AI "感觉好了"。

------------------------------------------------------------------------

# 9. 调试现场数据

如果问题难以现场复现，优先考虑保存：

-   必要视频 / 帧；
-   时间戳；
-   状态；
-   关键输入输出；
-   配置；
-   commit / 版本；
-   必要日志。

长期方向可参考 C++ Architecture 中的 Record → Replay，但不要为了一个简单
Bug 立即建设完整 Replay Framework。

------------------------------------------------------------------------

# 10. 结束条件

Debug 阶段结束不要求"系统永远不会再坏"。

只需要：

-   根因或主要因果关系有足够证据；
-   当前修复方案明确；
-   验证方法明确；
-   没有继续靠猜测叠保护。

然后切换到 Delivery / Integration。
