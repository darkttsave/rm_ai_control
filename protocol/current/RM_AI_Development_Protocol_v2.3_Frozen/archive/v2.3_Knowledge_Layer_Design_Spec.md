# RM AI Development Protocol v2.3
# Knowledge Layer Design Spec

> **Status：Design Freeze Candidate**
>
> **Target Version：v2.3 — Knowledge Learning & Note Lifecycle Patch**
>
> 本文件用于冻结 v2.3 的方法论、边界、对象职责、与 v2.2 的接轨方式，以及旧讲解 / 笔记 Skill 的迁移规则。
>
> 在本 Spec 经用户确认之前，不应直接把 v2.2 批量改造成 v2.3。
>
> v2.3 的目标不是建立新的“学习框架产品”，而是补齐现有 RM AI Development Protocol 中已经真实需要、但尚未正式系统化的知识学习与笔记生命周期。

---

# 0. 设计前提

v2.3 建立在 v2.2 已冻结能力之上，不重做已有系统。

当前正式基线：

```text
RM_AI_Development_Protocol_v2.2_Frozen
```

v2.3 必须继续遵守已有原则：

- RM 四问仍然是最高项目判断；
- 安全是硬约束；
- Good Idea ≠ Do It Now；
- Thinking Space 可以大，Code / Process Space 必须小；
- Incremental Development 必须形成 Convergence；
- Context / Handoff 采用 Minimum Sufficient Handoff；
- Checkpoint / Handoff 为事件驱动，而不是定时器；
- Conversation 与 Workspace 分离；
- Playbook 按需加载，不是启动时全部读取；
- Human Gate 只在真正需要人的工程意图时触发；
- 协议服务真实 RM 项目，而不是让项目服务协议。

---

# 1. v2.3 要解决什么

过去的知识学习规则分散在多代讲解 Skill、笔记重构 Skill、P0 学习产物和旧知识重构规范中。

这些规则已经积累出有价值的方法，但存在三个问题。

## 1.1 讲解与正式笔记混在一起

旧 Skill 往往同时要求：

```text
让用户理解
+
按照固定 Markdown 结构输出
+
生成 Obsidian 笔记
```

这会导致：

- 对话为了“文章完整”而失去自然性；
- 一个简单问题被扩展成完整课程；
- 正式笔记保留过多对话过程；
- 讲解规则和输出格式互相污染。

v2.3 必须明确：

> **Explanation 和 Note Output 是两套不同目标的系统。**

---

## 1.2 AI 缺少用户长期学习状态

新学习对话如果只看到当前问题，不知道：

- 用户已经学过什么；
- 哪些只是接触过；
- 哪些已经能用于工程；
- 哪些地方仍存在断点；
- 已经有哪些知识资产。

于是 AI 很容易：

- 从过低层级重新讲；
- 错过已有知识之间的联系；
- 把“存在笔记”误认为“已经掌握”；
- 再生成一份重复笔记。

v2.3 必须为知识对话提供长期状态输入。

---

## 1.3 学习对话缺少跨会话连续性

同一个知识主题可能经历：

```text
工程断点
→ 快速理解
→ 顺手记笔记
→ 一段时间后系统学习
→ 看源码
→ 再回工程
```

这些不应该被理解成互不相关的几个“知识项目”。

但也不能为了连续性，每讲一次就生成一次 Checkpoint。

v2.3 必须让知识学习复用 v2.2 的 Context / Handoff 机制，并只补充学习场景需要携带的 Payload。

---

# 2. 最高目标：Knowledge Sufficiency，而不是“完全掌握”

v2.3 不负责证明：

> “用户是否完全意义上掌握了某个知识。”

这种判断本身很难稳定定义，也没有必要成为工程协议目标。

Knowledge Layer 的目标是：

> **让用户当前的知识状态至少足以支撑真实项目中的使用、调参、诊断、修改和必要的工程判断。**

具体要求由当前项目责任决定。

---

## 2.1 复用 Engineering Control Ladder

v2.3 不新建另一套“掌握度等级”。

优先复用 v2.2 已有 Engineering Control Ladder：

| Level | 能力 | 典型判断 |
|---|---|---|
| L0 Reproduce | 跑起来 | 能否复现预期结果？ |
| L1 Operate | 会使用 | 知道入口、输入输出、日志和正常现象吗？ |
| L2 Tune | 会调 | 知道参数影响、范围、观测和回滚吗？ |
| L3 Diagnose | 会定位 | 能把异常缩小到合理模块或边界吗？ |
| L4 Modify | 会安全修改 | 理解约束、接口、影响范围和验证方法吗？ |
| L5 Explain | 能解释 | 能说明原理、工程语义和 trade-off 吗？ |
| L6 Reconstruct | 能重建 | 没有现成实现时能重新设计并验证吗？ |

不是所有知识都需要达到 L5 / L6。

---

## 2.2 学习退出条件来自项目，而不是知识体系

完整链路：

```text
Project / Development
        ↓
出现知识断点
        ↓
Learning / Knowledge Debt
判断：
现在值得学吗？
当前责任要求什么控制等级？
        ↓
Knowledge Layer
        ↓
Adaptive Explanation
        ↓
当前知识是否已经足够支撑任务？
        ├── Yes → 回到项目
        └── No  → 继续学习
```

例如：

```text
当前任务：调用 solvePnP
目标可能只要求 L1 / L2

当前任务：排查位姿跳变
目标可能要求 L3

当前任务：修改求解策略
目标可能要求 L4 / L5
```

因此：

> **Deep Study 不是学习完成的默认条件。**

---

# 3. Knowledge Layer 核心对象

v2.3 维护三个互相独立的状态对象。

```text
                 User Knowledge System
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
   Learning State   Knowledge Assets  Learning Thread
   人当前能做什么      库里有什么       这次学到哪里
          │              │              │
          └──────────────┼──────────────┘
                         ↓
                 Explanation Session
                         ↓
                 理解发生变化
                         ↓
           ┌─────────────┴─────────────┐
           ↓                           ↓
  Learning State Patch          Generate / Update Note
                                       ↓
                               Asset Index Update
```

---

# 4. Learning State

## 4.1 回答的问题

Learning State 回答：

> **用户在某个知识领域已经接触过什么、当前能支持哪些工程行为、还存在哪些会阻碍项目的知识断点？**

它描述“人”的状态。

它不描述知识库文件是否存在。

---

## 4.2 资产存在不等于掌握

必须写入核心约束：

```text
Knowledge Asset Exists
≠
User Has Mastered It
```

例如：

```text
有一篇 Homography 笔记
```

只能证明知识资产存在。

不能自动推出：

```text
用户能够独立解释 Homography；
用户能够使用它排查 PnP；
用户能够安全修改相关实现。
```

---

## 4.3 Learning State 推荐字段

第一版不使用掌握度百分比。

推荐记录：

```text
Topic / Area

Exposure:
- 是否接触过

Known:
- 已经形成的稳定理解

Current Engineering Control:
- 当前能支持到哪个工程控制行为
- 可以引用 L0~L6，但必须有具体说明

Gaps:
- 当前仍然存在的真实断点

Evidence / Experience:
- 什么经历支持当前判断

Project Relevance:
- 当前为什么重要

Suggested Next Trigger:
- 什么时候需要继续深入
```

不是每一项都必须有内容。

---

## 4.4 Learning State 的所有权

最终解释权属于用户。

AI 的职责：

```text
观察当前表现
→ 发现状态可能发生变化
→ 提出 Learning State Patch
→ 说明依据
```

AI 不应因为：

> “刚刚讲完一遍”

就自行宣布：

```text
Working → Solid
```

更不应把这种升级当成客观事实。

---

## 4.5 AI 什么时候可以提出 Patch

建议在以下事件发生时：

- 第一次形成对一个重要知识的有效理解；
- 原有重要 Gap 被解决；
- 原以为已掌握，但实际暴露出阻塞工程的断点；
- 用户通过真实工程使用证明新的控制能力；
- 用户已经能够 Diagnose / Modify 某一关键部分；
- 某个知识正式成为后续学习的可靠前置。

普通聊天不要求更新。

---

# 5. Knowledge Asset Index

## 5.1 回答的问题

Knowledge Asset Index 回答：

> **当前知识库已经有什么，以及每一份资产承担什么知识职责。**

它描述“知识库”。

它不能替代 Learning State。

---

## 5.2 最小字段

建议：

```text
Asset:
Path / Name:

Type:
- Theory / Concept
- API / Code
- System / Architecture
- Engineering / Project
- Source / Legacy

Status:
- Working
- Canonical
- Superseded
- Source

Coverage:
- 它主要回答什么

Relations:
- 前置 / 后续 / 强相关

Overlap / Responsibility:
- 是否和其他资产承担相同职责

Source / Provenance:
- 必要时记录来源
```

第一版不强制 UUID。

---

## 5.3 资产关系判断

不能使用：

> “同主题 = 必须合并”

正确判断是：

```text
同主题 + 不同职责
→ 可以共存，并建立关系

同主题 + 同职责
→ 检查 Update / Merge / Supersede
```

例如：

```text
solvePnP工程速用.md
→ API / Engineering Reference

平面PnP与IPPE.md
→ Theory / Deep Understanding
```

二者可以同时是 Canonical Asset。

---

## 5.4 资产生命周期

允许：

```text
Source Asset
原始旧笔记 / 视频 / 学习资料

Working Asset
当前学习过程中的临时产物

Canonical Asset
当前长期知识入口

Superseded Asset
已被新资产替代，但历史仍保留
```

v2.3 不要求用户启动时把全部旧笔记一次性登记。

采用：

> **Usage-driven Incremental Registration**

只有实际学习或工程中遇到相关领域时，再逐步登记已有资产。

---

# 6. Learning Thread State

## 6.1 定位

Learning Thread 是一个认知概念：

> **同一个学习主题跨多个对话 / 阶段的连续性。**

它不是长期数据库实体。

默认不需要：

- Thread ID；
- Thread Registry；
- Thread Manager；
- Thread History Database。

---

## 6.2 什么时候物化

只有以下事件才生成 `LEARNING_THREAD_STATE.md`：

- 当前对话准备更换；
- 当前学习阶段明显结束但未来还会继续；
- 重要认知被推翻；
- 当前 Context 已经难以稳定恢复；
- 形成了会影响后续学习的重要正式资产；
- 准备长期暂停。

---

## 6.3 最小内容

```text
Current Learning Goal

Confirmed Understanding

Important Corrections

Current Gaps

Relevant Knowledge Assets

Current Materials / Sources

Suggested Next Direction

Carry Forward
```

它不是完整聊天摘要。

新对话恢复后，也不要求持续维护 Thread State。

---

# 7. 初始化输入：系统上下文 + 用户 Learning Request

知识对话不能只依赖规范文件。

规范文件只告诉 AI：

> “怎样工作。”

用户还必须告诉 AI：

> “这一次为什么来学。”

因此 Bootstrap 分成两层。

---

## 7.1 系统 / 长期输入

根据环境按需提供：

```text
Knowledge Playbook / Entry

Learning State Overview
+
Relevant Learning State Detail

Knowledge Asset Overview
+
Relevant Asset Detail

如果是旧 Thread：
Learning Thread State

必要的 common continuity rules
```

---

## 7.2 用户本轮输入：Learning Request

使用模板，由用户自己填写真实意图。

建议字段：

```markdown
# Learning Request

## 我现在想解决什么

## 为什么现在需要它

## 我目前大概知道什么
可留空；Learning State 已经足够时不用重复。

## 本轮期望
例如：
- 先让我能读懂工程；
- 重点理解原理；
- 暂时不需要完整推导；
- 如果发现重要基础断点请提醒。

## 本轮材料
代码 / 文档 / 论文 / 视频 / 截图 / 项目背景等。
```

用户不需要填写：

```text
Subject = Theory
Depth = Deep Study
```

这些属于 AI 的内部路由。

---

# 8. Bootstrap 不能无限膨胀

长期设计采用：

```text
Global Overview
+
Relevant Detail
```

而不是每个新对话加载完整知识档案。

---

## 8.1 第一版实现

第一版可以仍然使用：

```text
LEARNING_STATE.md
KNOWLEDGE_ASSET_INDEX.md
```

但文件内部应支持按领域分区。

AI 在新任务中只抽取：

```text
全局概要
+
本轮相关领域
```

---

## 8.2 未来增长时

如果文件已经明显过长，再拆成：

```text
Overview
+
Domain Detail
```

这是允许的演化方向。

v2.3 不要求现在就建立复杂目录或数据库。

---

# 9. Explanation 与 Note Output 完全解耦

```text
Knowledge Common Principles
          │
   ┌──────┴──────┐
   ↓             ↓
Explanation     Note Output
让用户理解       形成长期资产
```

共享原则应非常薄：

- 不把推测写成事实；
- 术语和符号前后一致；
- 当前目标优先于模板完整性；
- 不为了“完整”扩展无关知识；
- 不确定时显式说明；
- 来源事实、解释和推断需要区分。

除此之外，两者独立。

---

# 10. Explanation System

## 10.1 唯一目标

> **让用户形成足以服务当前目标的正确理解。**

Explanation 不承担正式知识资产格式责任。

因此普通对话不应该为了笔记格式强制：

- 标题层级；
- Markdown 结构；
- 数学块格式；
- 第一屏；
- Obsidian 链接；
- 正式文章模板。

---

## 10.2 Explanation Core

通用规则：

1. 先找用户当前真正的认知断点；
2. 已有可靠前置不重复讲；
3. 真实断点才回退；
4. 优先回答“为什么现在需要这个概念”；
5. 理论、代码、API 和系统层次不要混成一句；
6. 必要时建立直觉模型，再进入数学或实现；
7. 利用 Learning State 主动连接已接触 / 已掌握知识；
8. “接触过”只可作为桥梁，不可作为跳过关键内容的证据；
9. 根据当前项目目标控制深度；
10. 理解足以支持当前项目后允许退出，不追求课程完整。

---

# 11. Explanation Profile：正交组合，而不是完整 Skill 堆叠

采用：

```text
Explanation Core
        +
Subject Profile
        +
Depth / Control Need
```

Profile 只定义相对 Core 的增量规则。

禁止在每个 Profile 中复制整套父规则。

---

## 11.1 Subject Profile

第一版逻辑分类：

### Theory / Concept

重点：

- 为什么引入；
- 直觉模型；
- 数学或物理关系；
- 条件与边界；
- 与已有知识连接；
- 必要时映射到工程。

### Code

重点：

```text
职责
→ 输入
→ 运行时状态变化
→ 输出
→ 下游
```

并按需区分：

```text
语言层
框架 / API 层
业务逻辑层
算法 / 原理层
```

同时区分：

- 当前代码显式完成什么；
- 被调用函数完成什么；
- 框架生命周期隐式完成什么；
- 什么只是推测。

### API / Framework

重点：

```text
调用者提供什么
→ API何时执行
→ 框架负责什么
→ 状态如何变化
→ 调用者得到什么
```

涉及版本差异时，优先明确版本和官方来源。

### System / Architecture

重点：

```text
上游输入
→ 当前模块职责
→ 核心状态
→ 模块关系
→ 输出
→ 失败边界
```

强调当前实现、设计意图和可替代方案的区别。

---

## 11.2 Depth / Control Need

v2.3 不把 Depth 当作用户必须选择的固定 Mode。

它是 AI 根据当前目标推断出的教学深度。

### Engineering Use

目标：

> 先能够正确使用。

主要回答：

- 它解决什么；
- 输入输出；
- 最小使用方式；
- 关键参数；
- 高频错误；
- 当前 Pipeline 位置；
- 出问题先查哪里。

### Working Understanding

目标：

> 能够 Tune / Diagnose / Modify 当前相关部分。

增加：

- 核心内部模型；
- 参数为什么影响结果；
- 关键假设；
- 失效模式；
- 输入如何影响输出；
- 调试证据。

### Deep Study

目标：

> 该知识已经成为长期核心能力，需要进入更完整的理论网络。

增加：

- 必要推导；
- 数学结构；
- 方法比较；
- 理论边界；
- 源码映射；
- 历史 / 现代扩展（只有真正有价值时）。

---

# 12. Intent-driven Adaptive Explanation

模式不由用户操作。

默认流程：

```text
用户表达真实需求
        ↓
AI 识别当前意图
        ↓
判断当前讲法是否仍适合
        ↓
动态调整 Subject / Depth / Teaching Strategy
```

---

## 12.1 三类变化

### A. Local Adjustment — 静默完成

例如：

- 临时补一个 C++ 语言点；
- 解释一个符号；
- 回答某个 API 参数。

无需提示“模式切换”。

---

### B. Meaningful Shift — 简短提醒后继续

例如用户从：

> “这个 API 怎么用？”

逐渐进入：

> “为什么在几何上会有两解？”

AI 应简短说明：

- 为什么判断方向已经变化；
- 接下来大致会进入哪些内容；
- 已理解部分不会重复。

推荐长度：

> 1～3 句。

不要输出长状态报告。

---

### C. Scope Expansion — 说明代价并询问

如果当前单点问题继续深入会显著扩大：

- 学习时间；
- 知识范围；
- 当前项目 Scope；

则 AI 应提示：

```text
现在的问题只需要哪一层
+
继续深入会进入什么完整知识链
+
当前工程是否真的需要
```

只有这种情况才需要用户确认。

---

# 13. 已有知识如何参与新讲解

Learning State 的价值之一是建立跨领域连接。

AI 可以主动说：

> “这里与你之前接触过的 EKF 状态转移是同一种建模思想……”

但必须遵守：

```text
Exposed
→ 可以作为熟悉感和桥梁

Known / Engineering Control 有证据
→ 可以作为可靠前置

Asset Exists
→ 只能说明可以引用该资产
```

如果当前表现与 Learning State 冲突：

> 当前对话证据优先用于本轮讲解，并建议后续 Patch。

---

# 14. Note Output System

## 14.1 目标

> **把已经形成的理解重新组织成可快速恢复、长期维护、能继续扩展的知识资产。**

不是：

- 聊天记录摘要；
- 完整教学过程复刻；
- 为了显得完整加入大量背景；
- 每出现一个名词就新建一个文件。

---

## 14.2 Note Core

正式笔记默认遵守：

1. 按知识依赖组织，不按聊天顺序组织；
2. 一篇保持一条中心主线；
3. 快速复习信息前置；
4. 标题短、明确、可扫描；
5. 图、公式、代码都承担明确认知任务；
6. 讲解可以展开，正式笔记必须收紧；
7. 保留长期有价值的误区与纠错结论；
8. 删除无长期价值的对话往返；
9. 来源事实、解释、工程推断分层；
10. 回到当前系统 / 工程中的位置；
11. 不因为“更高级”就加入无关扩展；
12. 不机械追求短，也不无限扩张。

---

不进入 Explanation Core。

至少覆盖：

- 标题命名；
- 标题层级；
- 第一屏结构；
- 行内公式与块公式；
- LaTeX 风格；
- 变量首次出现时的解释；
- 代码块语言标识；
- 最小代码示例；

- Obsidian 内部链接；
- “一些问题 / 易混点 / 边界”的组织方式；

# 17. AI 什么时候可以主动提示生成 / 更新笔记

允许，但必须克制。

建议只在：

- 一条知识主线已经明显闭合；
- 一个重要误区已经稳定解决；
- 一个模型已经具有长期复用价值；
- 当前已有 Canonical Asset 很适合更新；
- Deep Study 阶段准备结束；
- 当前学习成果如果不保存，很可能影响后续连续性；

时提示。

提醒应短。

例如：

> 这一段已经形成完整的“平面 PnP 多解”知识链，而且现有资产里有对应理论笔记，更适合更新原笔记，不必另建一篇。

AI 不自动制造正式知识资产。

最终是否生成仍由用户决定。

# 18. Legacy Reconstruction

旧知识重构不是所有笔记的默认模式。

它是：

```text
Note Operation = Legacy Reconstruction
```

主要继承旧 `knowledge-note-refactor` 的规则：

- 原始来源默认只读；
- Semantic Coverage；
- 保留原任务事实；
- 保留有长期价值的用户原创内容；
- 保留历史验证状态；
- 技术校正必须区分原始内容和后续修正；
- 链接不能替代主干必要解释；
- 任务驱动笔记保留问题 / 代码 / 结果之间的关系；
- 必要时分批审批。

Legacy Reconstruction 不要求污染普通 New Note。

# 30. Frozen Decisions

以下在 v2.3 视为冻结。

1. Knowledge Layer 服务真实项目，而不是追求“完全掌握”。
2. Knowledge Sufficiency 由当前工程责任决定。
3. 不创建新的掌握度百分比系统。
4. Learning State 与 Knowledge Asset State 必须分离。
5. Learning Thread 只在必要时物化。
6. Learning State 最终解释权属于用户。
7. AI 只提出长期状态 Patch，不自行宣布用户“掌握”。
8. Bootstrap 使用 `Overview + Relevant Detail`，禁止无限膨胀。
9. 用户通过 Learning Request 表达真实目标，不操作 Mode。
10. Subject / Depth / Teaching Strategy 由 AI 主动路由。
11. 局部变化静默；明显变化简短提示；重大范围扩展才询问。
12. Explanation 和 Note Output 完全解耦。
13. Note Style 不进入 Explanation。
14. AI 可以克制地建议形成 / 更新笔记，但不自动制造正式资产。
15. 同主题不同职责资产允许共存。
16. 同职责重复资产才进入 Update / Merge / Supersede。
17. Legacy Reconstruction 是 Note Operation，不是所有 Note 的默认规则。
18. v2.3 必须复用 v2.2 common / Specialist / Engineering Control / Debug 等已有能力。
19. Knowledge Layer 只增加领域 Payload 和学习 / 笔记方法，不复制 Context / Debug / Development 系统。
20. 用户可见正式产物继续遵守 Artifact Generation Contract。
21. 旧 Skill 是来源资产，不原样成为 v2.3 正式规则。
22. v2.3 第一版坚持 Markdown、人可读、低自动化。
