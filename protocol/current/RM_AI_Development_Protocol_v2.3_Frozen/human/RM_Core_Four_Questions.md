# RM 工程四问

> 这是 v2.3 继续沿用的最高层判断框架。\
> 所有设计、开发、AI
> 协作、调试、重构和学习行为，都应该服务于这四问，而不是为了流程本身存在。

------------------------------------------------------------------------

# 0. 为什么造？

> **这个任务解决什么真实问题，为什么现在值得做？**

在传承优秀的 RM
队伍中，方向往往来自学长、历史赛季和成熟工程经验，因此新人不需要为了"独立思考"而刻意反对传承。

但"相信经验"不能演变成"停止理解"。

至少逐渐知道：

-   当前瓶颈是什么；
-   为什么这个任务现在优先；
-   它与规则、机械、电控、算法和比赛策略是什么关系；
-   哪些前提一旦变化，优先级可能需要重新判断。

推荐成长路径：

``` text
先相信成熟传承
→ 在执行中理解原因
→ 能判断前提是否仍成立
→ 能参与技术优先级讨论
→ 最终有能力产生下一代判断
```

这一问主要防止：

-   被 AI 带着不断"下一步"；
-   局部优化抢占主目标；
-   做出很漂亮但当前没有比赛价值的系统。

------------------------------------------------------------------------

# 1. 造不造得出来？

> **能不能在真实时间、硬件和团队约束下形成比赛需要的完整闭环？**

RM 的工程结果不是局部 Demo，而是：

``` text
真实输入
→ 算法 / 状态
→ 通信 / 决策
→ 执行
→ 机器人完成任务
```

因此"能造出来"至少包括：

-   能 Reproduce；
-   能 Operate；
-   有 Walking Skeleton；
-   能尽早 Integration；
-   能达到当前任务要求的 Verification Level；
-   能在比赛 Deadline 前交付。

> 比赛前无法落地的方案，在工程意义上就是当前造不出来。

这一问主要防止：

-   只研究架构不形成闭环；
-   只做单模块 Demo；
-   完整理解后才允许开发；
-   把"理论可行"当"工程完成"。

------------------------------------------------------------------------

# 2. 稳不稳定？

> **机器人能否可靠运行，代码能否持续维护和迭代，团队能否接得住？**

稳定至少包括三层。

## 运行稳定

-   合理失败行为；
-   必要超时 / 限幅 / 边界；
-   性能满足需求；
-   真实环境下能重复工作。

## 工程稳定

-   模块职责清楚；
-   Interface 相对稳定；
-   新需求不会牵动大量无关代码；
-   Debug / Observability 不污染主线；
-   死亡代码会被删除；
-   Temporary 不会永久化；
-   重要 Milestone 后能够收敛。

## 团队稳定

-   不是只有原作者能维护；
-   当前关键参数和故障入口可被接管；
-   项目事实不依赖某一个聊天窗口或个人记忆。

这一问主要防止：

-   "今天能跑"就等于稳定；
-   最小修改演变成补丁堆积；
-   过度设计和无意义兼容；
-   代码只对作者本人可维护。

------------------------------------------------------------------------

# 3. 出了问题会不会修？

> **是否掌握关键链路，能够获得证据、缩小故障域、验证假设并证明修复有效？**

"会修"不意味着所有 Bug 都能立即知道答案。

而是至少能：

``` text
观察现象
→ 区分 Fact / Hypothesis / Unknown
→ 知道关键数据流
→ 缩小故障域
→ 选择高信息量实验
→ 获得证据
→ 修改
→ 验证修复
```

如果系统一出问题只能：

``` text
复制日志给 AI
→ AI 说改 A
→ 不行再改 B
→ 再叠 C
```

即使当前车能跑，也还没有真正掌握系统。

这一问主要对应：

-   Investigation / Experiment；
-   Engineering Control Ladder；
-   Knowledge Debt；
-   Observability；
-   Record / Replay；
-   Debug Playbook；
-   "如果坏了，第一步查哪里？"的 Cognitive Gate。

------------------------------------------------------------------------

# 安全：四问下面的硬约束

安全不是第五问，因为它不是与性能、速度、维护性并列的优化目标。

它是硬边界。

涉及真实执行器、机械、能源或人员风险时：

> **不能用不可接受的安全风险交换"更快造出来""更高性能"或"更简单实现"。**

------------------------------------------------------------------------

# 四问的相互制约

只追"造出来"：容易得到能跑但不可维护的补丁工程。\
只追"稳定"：容易为了架构完整迟迟不上车。\
只追"会修"：容易把所有知识都学懂后才允许开发。\
只追"为什么造"：容易停留在战略讨论而不交付。

真正健康的是四者共同成立。

------------------------------------------------------------------------

# 所有新复杂度的快速过滤器

面对一个新 Framework、Manager、Tool、模式、流程或 AI 建议，先问：

1.  它是否明显帮助"为什么造"的目标更清楚？
2.  它是否明显帮助"造得出来"？
3.  它是否明显提高运行 / 工程 / 团队稳定性？
4.  它是否明显帮助故障复现、定位和修复？

如果都不能：

> 默认不加入系统。

这不是禁止探索，而是让复杂度必须对真实工程价值负责。
