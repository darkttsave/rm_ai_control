# Human Core --- RM 开发者核心约定（v2.3；继承 v2.2）

> 只给人阅读。AI 不需要加载。\
> v2.3 继续沿用 v2.2 的组织方式：不把十几条规则当作同级清单，而是围绕 RM 工程四问组织人的行为。

------------------------------------------------------------------------

# 一、为什么造：守住主线

1.  始终知道当前 Milestone 为什么存在。
2.  尊重优秀传承，但逐渐理解任务判断的依据。
3.  开发途中出现"更漂亮的优化"时，默认先记录，不自动获得执行权。
4.  如果已经说不清最初为什么开始这项修改，停止扩张，回到主线。

------------------------------------------------------------------------

# 二、造不造得出来：优先形成真实闭环

1.  先 Walking Skeleton，再按真实风险增量强化。
2.  尽早接真实边界，不把所有模块"做完"后才第一次联调。
3.  时间紧时允许 Minimum Viable Learning，不要求先完成课程式学习。
4.  不能验证就诚实停在当前 Verification
    Level，不用推测性代码掩盖外部依赖未完成。
5.  已有成熟仓库先 Reproduce / Operate，再谈重构。

------------------------------------------------------------------------

# 三、稳不稳定：让系统能够继续活下去

1.  不提前实现未经证实的未来。
2.  已死亡的过去要敢删；历史交给 Git。
3.  Temporary 必须知道什么时候删除。
4.  重要 Milestone 后主动收敛旧 API、重复路径、无使用者配置和调试污染。
5.  代码不仅要自己能维护，也要让团队能接手。
6.  真机安全决策最终由人负责。

------------------------------------------------------------------------

# 四、出了问题会不会修：保持工程控制力

1.  Fact、Hypothesis、Unknown 必须分开。
2.  调试目标是获得证据，不是继续改代码。
3.  一次实验尽量回答一个主要问题。
4.  允许 Knowledge Debt，但不能隐形、不能无限扩张。
5.  准备 Tune / Diagnose / Modify / Robot Integration
    前，补齐对应层级的最低理解。
6.  对关键模块始终能回答：

> **如果现在坏了，我第一步查哪里？**

如果答案长期只能是"再问 AI"，说明认知债务已经超过可接受范围。

------------------------------------------------------------------------

# 五、人的总职责

AI 可以：

-   查资料；
-   读代码；
-   分析日志；
-   提方案；
-   写代码；
-   跑测试；
-   整理报告。

人始终负责：

-   当前目标；
-   真实机器人事实；
-   重大工程意图；
-   安全；
-   是否接受实验结论；
-   哪个问题现在最值得解决；
-   最终是否认为系统已经可控。

------------------------------------------------------------------------

# 一句话版本

> **先确认为什么造，再把它真正造出来；让它稳定地活下去，并保证坏了以后自己知道怎么修。**
